# 05. 时序记忆与数据设计

## 1. 设计前提

用户认为同一份聊天记录没有必要在平台和 Yance 中长期保存两份。因此本方案采用：

- **默认不长期复制聊天正文**；
- 长期保存消息元数据、来源引用、蒸馏结果和用户纠正；
- 需要逐字证据或重新分析时，按来源 ID 重新请求原平台或用户导入档案；
- 原文是否短期加密缓存不是绝对禁令，但必须由用户按数据源选择。

这个选择降低存储和隐私暴露，但代价明确：连接器失效、平台删除消息或用户失去账号后，Yance 无法离线逐字复核，也无法完整重跑历史模型。

## 2. 数据分层

### L0：来源引用层

保留：

- 平台、账号、会话和消息稳定 ID；
- 发送时间、采集时间、发送方、接收方；
- 回复/引用关系、消息类型、内容 hash；
- 来源是否仍可访问、最后核验时间；
- 用户导入档案的位置和版本。

聊天正文默认只在分析过程中临时存在，不进入长期日志。

### L1：互动事件层

将消息组织为可检索的情节：

- 一次催进度；
- 一段价格谈判；
- 一次争执和修复；
- 一次明确边界；
- 一次工作、居住或关系变化。

事件包含参与者、时间范围、主题、转折和来源消息 ID，不复制整段原文。

### L2：原子观察与事实层

区分两类内容：

- **可验证事实**：例如“对方明确说周五前需要结果”；
- **行为观察**：例如“最近 30 天主动开启话题次数下降”。

每项带主体、字段、值、有效时间、记录时间、来源、支持/反对证据、置信分量和状态。

### L3：人物与关系状态层

包括：

- 人格维度候选；
- 当前压力、表达倾向和沟通习惯；
- 关系中的信任、边界、冲突与修复状态；
- 重要偏好、禁忌和历史承诺；
- 当前身份与沟通目标。

状态是派生物，不是原始真相。

### L4：阶段画像层

同时沿两条轴生成：

- **周期轴**：周回顾、月画像；
- **事件轴**：重大冲突、关系转折、搬家、入职、交易纠纷等快照。

快照记录变化、证据覆盖、冲突和未知项，不用一个新摘要覆盖所有历史。

### L5：查询证据包

每次回答只临时组装：

- 当前问题需要的状态；
- 关键事件和变化；
- 支持与反对证据摘要；
- 必要时从 MCP 临时读取的少量原文；
- 上下文缺失和不确定项。

证据包使用后删除或按短期缓存策略处理。

## 3. 核心概念

| 概念 | 作用 |
| --- | --- |
| Person | 真实人物的本地逻辑身份 |
| Platform Identity | 人物在某个平台和账号下的身份 |
| Relationship | 用户与人物在特定关系/场景中的联系 |
| Conversation | 平台会话或导入会话 |
| Message Reference | 不含长期正文的消息来源、元数据和 hash |
| Interaction Event | 多条消息形成的情节或现实事件 |
| Observation / Claim | 可验证事实或行为观察 |
| Evidence Link | 观察与消息来源之间的支持、反对、更正关系 |
| Trait Hypothesis | MBTI、行为维度或情感倾向假设 |
| Profile Snapshot | 周/月/重大事件的人物或关系快照 |
| User Correction | 用户对人物关联、身份、事实和画像的明确纠正 |

跨平台人物合并由 AI 提议、用户确认。合并保留各平台身份，不把昵称相似自动当作同一个人。

## 4. 双时间

每个事实或状态至少区分：

- **有效时间**：现实中何时成立；
- **记录时间**：Yance 何时得知、抽取或更正。

例如用户在 10 月才导入一条“3 月已搬到上海”的消息：有效时间从 3 月开始，记录时间是 10 月。这样既能回答“当时是什么状态”，也能回答“系统当时知道什么”。

## 5. 字段级时间线

人物画像不能是可覆盖的单一 JSON 大对象。每个重要字段保留多个时间版本：

- MBTI 四维倾向；
- 主动发起、回复延迟、直接程度、温暖表达；
- 偏好、边界和条件；
- 关系信任、冲突和修复；
- 当前工作、居住和计划；
- 短期压力与情感表达。

长期属性、阶段状态、计划、事件、他人转述和模型推断必须分开，不能互相覆盖。

## 6. 证据、置信与冲突

不得只保存模型自报的 `0.87`。置信由多个部分组成：

- 抽取是否清楚；
- 来源是本人直接陈述、用户转述还是模型推测；
- 支持证据是否跨时间重复；
- 时间是否确定；
- 是否存在反证或明确更正；
- 当前状态是否可能已经过期；
- 数据覆盖是否足够。

界面优先显示：`证据不足 / 较弱 / 中等 / 用户确认 / 存在冲突 / 已失效`。

冲突值同时保留并指向各自来源。选择当前状态时，用户明确纠正优先，其次是更近且时间清楚的直接陈述；无法判断时返回冲突，不静默选边。

## 7. 更正、删除与重建

- 用户更正不会伪装成原始消息，而是新增一条纠正记录。
- 新事实可以替代或使旧事实失效，但旧认知版本在允许保留的审计范围内可追溯。
- 用户删除某联系人画像时，应删除相关画像、观察、证据摘要、跨平台关联和缓存；来源平台原文不受 Yance 控制。
- 用户删除某个时间段后，后续快照需要重新计算。
- 模型或提示版本变化时，只重建受影响字段和快照，不全库盲目重跑。

隐私物理删除优先于不可变审计需求；对被删除数据不能以“事件不可变”为由继续保留。

## 8. 周期与事件蒸馏

- 新消息到达只做轻分析和增量水位更新；
- 用户打开会话时进行按需深分析；
- 重大事件即时形成候选快照；
- 每周生成低成本关系回顾；
- 每月生成阶段画像和变化说明；
- 新证据影响历史时，只标记相关字段和后续快照待重建。

每次变化必须区分：

- 观察到的行为变化；
- 消息数量、渠道和话题构成变化；
- 可能情境事件；
- 是否持续多个窗口；
- 是否只是模型输出波动。

## 9. token 高效检索

1. 先识别人、关系、字段、事件和时间范围；
2. 先用结构化元数据过滤；
3. 读取事件和字段轨迹摘要；
4. 只对命中的来源 ID 请求必要原文；
5. 同时保留支持、反对和未知项；
6. 按固定 token 预算组装证据包；
7. 证据不足时拒绝继续推断或向用户提问。

首版先使用关系型索引和全文检索处理用户导入档案；只有评测证明召回不足时才引入向量检索。无需先上图数据库。

## 10. 存储形态建议

规划层面采用：

- 关系型存储管理身份、时间、来源、状态、冲突和索引；
- JSON 承载仍在变化的人物维度、事件详情和画像正文；
- 用户导入的原始档案保持独立并由用户决定保留；
- 本地密钥与文件加密属于实现前必须完成的安全设计。

具体数据库产品在实现阶段冻结；SQLite 是适合 macOS 本地首版的候选，但不是本轮 Markdown 规划的交付内容。

## 11. 摘要漂移防线

- 画像中的每个重要结论必须有来源 ID；
- 新快照不能只总结旧快照，必须读取本期变化和抽样来源；
- 事实、推测、关系解读和待确认问题分栏；
- 新增断言无来源时不得固化；
- 反证、否定、撤回和冲突不能在摘要中消失；
- 定期从字段轨迹重建，而不是无限摘要套摘要。
